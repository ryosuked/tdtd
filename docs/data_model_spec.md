# データモデル仕様（schemaVersion 2）

データの形の正はこの文書。保存の形と構造を選んだ理由は [ADR-0001](adr/0001-storage-and-structure.md)。

## 1. 全体像

```text
Application Support/<アプリ>/
├── workspaces/
│   ├── <workspaceId>.json   # ワークスペース 1 つ = 1 ファイル（§2〜§5）。エクスポートしてもこのまま
│   └── ...
├── damaged/                 # 起動時に読めなかったファイルの退避先（§8）
└── app_state.json           # 表示の状態。エクスポートしない（§6）
```

```text
WorkspaceFile
└── workspace: Workspace
    └── categories: [Category]   # 配列の順 = 表示の順
        └── tasks: [TodoItem]    # 配列の順 = 表示の順
```

- **入れ子にする**: タスクはカテゴリの中にだけ置く。どのカテゴリにも属さないタスクは、形の上でありえない
- **並び順は配列の順そのもの**: `order` のような欄は持たない
- **保存するデータと表示の状態を分ける**: 表示モード・完了したタスクを隠すか・畳んだカテゴリは `app_state.json` に置く

## 2. ワークスペースのファイル（例）

```json
{
  "format" : "todo-workspace",
  "schemaVersion" : 2,
  "workspace" : {
    "categories" : [
      {
        "color" : "blue",
        "createdAt" : "2026-10-23T08:00:00.000Z",
        "id" : "0D3A6C2E-5B1F-4E2A-9C61-2F1B7A9E4C10",
        "name" : "企画",
        "tasks" : [
          {
            "content" : "見積もりを出す\n先方に確認してから",
            "createdAt" : "2026-10-23T08:01:00.000Z",
            "due" : "2026-10-30",
            "id" : "A7E2F1B4-3C5D-4E6F-8A9B-0C1D2E3F4A5B"
          }
        ]
      }
    ],
    "createdAt" : "2026-10-23T08:00:00.000Z",
    "id" : "6F1C2D3E-4A5B-4C6D-8E7F-9A0B1C2D3E4F",
    "name" : "仕事",
    "updatedAt" : "2026-10-23T08:01:00.000Z"
  }
}
```

未完了のタスクには `completedAt` のキーが無い（§5）。

## 3. 項目の定義

### WorkspaceFile（ファイルのいちばん外側）

| 項目 | 型 | 必須 | 決まり |
|---|---|---|---|
| `format` | 文字列 | ✓ | `"todo-workspace"` と一致する。別のアプリの JSON を取り違えないための印 |
| `schemaVersion` | 整数 | ✓ | `2`。`1` は読むときに移す（§10）。アプリが知っている版より新しければ拒否する |
| `workspace` | Workspace | ✓ | |

### Workspace

| 項目 | 型 | 必須 | 決まり |
|---|---|---|---|
| `id` | UUID | ✓ | |
| `name` | 文字列 | ✓ | 1〜100 文字。改行を含まない。前後が空白だけのものは不可 |
| `categories` | Category の配列 | ✓ | 0 個でもよい |
| `createdAt` | 日時 | ✓ | |
| `updatedAt` | 日時 | ✓ | ファイルの中の、どこかが最後に変わった日時（§4） |

### Category

| 項目 | 型 | 必須 | 決まり |
|---|---|---|---|
| `id` | UUID | ✓ | |
| `name` | 文字列 | ✓ | 1〜100 文字。改行を含まない。空白だけは不可 |
| `color` | 色名 | ✓ | §3.1 の一覧のどれか |
| `tasks` | TodoItem の配列 | ✓ | 0 個でもよい |
| `createdAt` | 日時 | ✓ | |

### TodoItem（タスク）

Swift の型名は `TodoItem` にする。`Task` は Swift の並行処理の `Task` とぶつかるため。

| 項目 | 型 | 必須 | 決まり |
|---|---|---|---|
| `id` | UUID | ✓ | |
| `content` | 文字列 | ✓ | タスクの中身。**書式なしの文字列だけ**（太字・リンク・画像などの書式は持たない。意図して決めた。requirements F3-1）。§3.3 の正規化をした形で持つ。1〜100,000 文字。改行してよい。空白と改行だけのものは不可。タイトルとメモには分けない（一覧では冒頭の 3 行だけを出す） |
| `due` | 日付 | | 期限。無ければキーを省く |
| `completedAt` | 日時 | | 完了した日時。キーが無ければ未完了。「完了か」と「いつ完了したか」を別々に持つと食い違いうるので、1 つにまとめる |
| `createdAt` | 日時 | ✓ | |

### 3.1 色名

`gray` `red` `orange` `yellow` `green` `teal` `blue` `indigo` `purple` `pink`

16 進の色値にはしない。ライト・ダークで実際の色を差し替えられるようにするため。新しく作ったカテゴリは `gray`。

### 3.2 値の書式

| 型 | 書式 | 決まり |
|---|---|---|
| UUID | `8-4-4-4-12` の 16 進 | 書くときは大文字（Swift の `uuidString` のまま）。読むときは小文字も受け付ける。同じかどうかは値で比べる |
| 日時 | ISO 8601、UTC、ミリ秒付き `2026-10-23T08:00:00.000Z` | 読むときはミリ秒なし（`…:00Z`）も受け付ける。小数は 3 桁だけ。UTC 以外（`+09:00` など）は誤り。中核は日時をミリ秒に丸めて打つので、読んで書き直しても値が変わらない。切り捨てにしないのは、浮動小数点の誤差で 1 ms 下がることがあるため。ミリ秒の部分は整数として自前で読み書きする（Foundation の書式は小数を切り捨て、`.999` が `.998` になる） |
| 日付 | `YYYY-MM-DD` | 実在する日付（グレゴリオ暦）に限る。日時にしないのは、タイムゾーンによって日付がずれないようにするため。Swift では `LocalDate { year, month, day }` として持つ |
| 文字数 | Swift の `String.count`（書記素クラスタ） | 見た目の 1 文字を 1 と数える。§3.3 の正規化の後で数える |

### 3.3 文字列の正規化

すべての文字列（名前と `content`）は、次の形にそろえて持つ。書式付きのテキストを貼り付けたときに混ざる、改行のつもりの文字や見えない文字を片付けるため。処理は TodoCore の 1 つの関数にまとめ、**入力（§4 の操作）と読み込み（§5）の両方**で通す。

| 元の文字 | よく出る元 | そろえ方 |
|---|---|---|
| CR LF（`\r\n`） | Windows のアプリ、Excel、Word | LF（`\n`）1 つ。CR と LF を別々の改行にしない（2 重にしない） |
| CR（`\r`）だけ | 古い形式のテキスト | LF |
| U+2028 行区切り、U+2029 段落区切り、U+0085 NEL | メモ、Pages、Web の `<br>` | LF |
| U+000B 垂直タブ、U+000C 改ページ | Word の手動の改行・改ページ | LF |
| U+FFFC（画像や添付の位置）、U+FEFF（BOM） | 画像入りの文、ファイルの先頭 | 取り除く |
| そのほかの制御文字（U+0000〜U+001F・U+007F〜U+009F。タブと LF は除く） | 壊れたテキスト | 取り除く |

- 変えないもの: タブ、空行（2 重の改行も、元から 2 つあればそのまま）、ノーブレークスペース、ゼロ幅接合子（絵文字の結合に要る）などの、そのほかの文字
- 読み込みで誤りにせず、そろえて読む。そろえる前の版で保存されたファイルを退避させないため。UUID の大文字・小文字をそろえるのと同じ扱い
- そろえた後に、長さ・改行・空白だけの決まり（V5）をかける。名前は、そろえた後に改行が残れば誤り

## 4. 操作

中核の操作は純粋関数で、現在時刻は引数 `now` で受け取る（中核の中で `Date()` を呼ばない）。どの操作でも `workspace.updatedAt = now` にする。ワークスペースの一覧に「最終更新」を出すのに使う。

カテゴリとタスクは `updatedAt` を持たない。同期をしないので使い道が無いため（[ADR-0001](adr/0001-storage-and-structure.md)）。

| 操作 | 中身 |
|---|---|
| ワークスペースの名前の変更 | |
| カテゴリの追加 | 末尾に足す。`createdAt` は `now` |
| カテゴリの名前・色の変更 | |
| カテゴリの並べ替え | 配列の中で動かす |
| カテゴリの削除 | 中のタスクも消える |
| タスクの追加 | カテゴリの末尾に足す。`createdAt` は `now` |
| タスクの中身の変更 | `content` を置き換える |
| 期限の変更 | `due` を置き換える。nil で外す |
| 完了・未完了の切り替え | `completedAt` を `now`／なしにする |
| タスクの並べ替え（同じカテゴリの中） | 配列の中で動かす |
| タスクを別のカテゴリへ移す | 抜いて、移す先の指定の位置へ差し込む |
| タスクの削除 | |

- 変わる値が無い操作（同じ名前への変更など）は、何もしない。`workspace.updatedAt` も動かさない

## 5. 不変条件と検証

読み込み（起動時・インポート）では、次のどれかに当たったらファイル全体を拒否する。文字列の決まり（V5）は TodoCore の 1 か所に置き、操作（§4）も同じ決まりで確かめる。決まりに合わない操作は誤りにして、データを変えない。勝手に直さない。最初に見つけた誤りを、場所（例: `workspace.categories[2].tasks[5].due`）と一緒に返す。

| # | 決まり |
|---|---|
| V1 | JSON として読める。UTF-8 |
| V2 | `format` が `"todo-workspace"`、`schemaVersion` が `1` か `2` |
| V3 | 必須の項目がある。型が合っている |
| V4 | UUID・日時・日付・色名が §3 の書式に合う。日付は実在する |
| V5 | 文字列の長さと改行の決まりを守っている（§3）。§3.3 の正規化の後で確かめる |
| V6 | ファイルの中の ID がすべて異なる（ワークスペース・カテゴリ・タスクを通して） |

- **知らない項目は捨てる**。誤りにはしない。古いアプリでも、新しい版で足した任意の項目を含むファイルを読めるようにするため（ただし V2 で版が新しければ拒否する）
- 任意の項目（`due`・`completedAt`）は、キーが無くても `null` でも「無し」と見なす。書くときはキーを省く
- `updatedAt` が `createdAt` より前でも誤りにしない。端末の時計がずれることがあるため
- 書き出し: JSON、UTF-8、`.prettyPrinted` ＋ `.sortedKeys` ＋ `.withoutEscapingSlashes`。キーの順を固定し、比べやすくするため
- **往復の一致**: 正しいファイルを読んで書いた結果は、JSON の値として元と一致する（キーの並びや空白の違いは問わない。ただし、元が小文字の UUID・ミリ秒なしの日時・`null` の任意の項目・§3.3 でそろえる文字を含む文字列だったときは、書いた側の形に正規化される）

## 6. `app_state.json`（表示の状態）

```json
{
  "schemaVersion" : 1,
  "workspaceOrder" : ["6F1C…", "…"],
  "lastOpenedWorkspaceId" : "6F1C…",
  "workspaces" : {
    "6F1C…" : {
      "displayMode" : "columns",
      "hideCompleted" : false,
      "collapsedCategoryIds" : [],
      "lastUsedCategoryId" : "0D3A…"
    }
  }
}
```

| 項目 | 決まり |
|---|---|
| `displayMode` | `"columns"`（短冊）か `"list"`（1 欄）。初めは `"columns"` |
| `collapsedCategoryIds` | 1 欄表示で畳んでいるカテゴリ |
| `lastUsedCategoryId` | 1 欄表示でタスクを足すとき、最初に選ばれているカテゴリ（requirements F4-5） |

- このファイルは失っても困らない。壊れていたら、黙って初めの値に戻す（ワークスペースのファイルとは扱いを分ける）
- 実在しない ID は読むときに無視する
- `workspaceOrder` に無いワークスペースのファイルは、`createdAt` の順に末尾へ足す

## 7. 上限

| 対象 | 上限 | 根拠 |
|---|---|---|
| インポートするファイルの大きさ | 20 MB | 性能の目安（5,000 件 ≒ 2 MB、requirements §4）の 10 倍。これより大きいものは読み込む前に断り、メモリを守る |
| 名前（ワークスペース・カテゴリ） | 100 文字 | 一覧や列の見出しに 1 行で出すため |
| タスクの中身（`content`） | 100,000 文字 | 保存はファイル全体の書き直しなので、1 件の大きさが毎回の保存の重さになる。日本語は UTF-8 で 1 文字 3 バイトなので、約 300 KB。長い文章を貼っても切られず、1 件でファイルを膨らませすぎない線。表示の重さは、冒頭だけを切り出して出すので長さに左右されない |

件数（カテゴリ数・タスク数）には上限を設けない。ファイルの大きさの上限で間接的に抑える。

## 8. 保存と読み込みの手順

| 場面 | 手順 |
|---|---|
| 変更したとき | 1 秒待ってから、そのワークスペースのファイルを書く。待つ間に次の変更があれば、待ち直す。1 文字打つたびに書かないため |
| 背面に回る・終了するとき | 待たずにすぐ書く |
| 書き方 | MainActor の外でエンコードする。書く前に、エンコードした結果を読み込みの検証（§5）にかけ、通らなければ書かずに誤りを出す（自分で読めないファイルを書かないため）。通ったら `Data.write(options: .atomic)` で置き換える。エクスポートも同じ確かめをする |
| 書けなかったとき | メモリの中のデータは残す。誤りを 1 か所に出す。次の変更のときに書き直す |
| 起動時に読めないファイルがあったとき | 上書きしない。`damaged/` へ移して知らせる。ほかのワークスペースはそのまま開く |

## 9. インポート・エクスポート

| 操作 | 決まり |
|---|---|
| エクスポート | 保存中のファイルと同じ中身を、整形した JSON のテキストとして書き出す。表示の状態（`app_state.json`）は含めない。拡張子は未決（[OPEN_ITEMS](../OPEN_ITEMS.md)） |
| インポート（新しい ID） | 検証（§5）に通ったら、そのまま追加する。`workspaceOrder` の末尾に足す |
| インポート（ID がすでにある）→ 置き換える | ファイルを差し替える。表示の状態はそのまま使い、実在しなくなった ID は無視する |
| インポート（ID がすでにある）→ 複製として追加 | ワークスペース・カテゴリ・タスクの ID を、すべて新しく振り直す。日時と名前はそのまま |

## 10. スキーマを変えるとき

- `schemaVersion` を上げる。この文書に変更履歴と移行の規則を、同じ変更の中で書く
- 古い版のファイルは、読むときに新しい版へ移す。移した結果は、次に保存するときに新しい版で書く
- 版を上げずに足してよいのは、任意の項目だけ（古いアプリは知らない項目を捨てるので、壊れない）。ただし、古いアプリで開いて保存すると、その項目は消える

### 10.1 版 1 → 版 2 の移し方

| 版 1 | 版 2 |
|---|---|
| `title`（1〜500 文字） と `note`（0〜20,000 文字） | `content` = `note` が空なら `title`、そうでなければ `title` ＋改行＋ `note` |
| そのほかの項目 | そのまま |

- 版 1 の `title` は改行を含まない決まりだったが、版 1 のアプリは入力の改行を止めておらず、改行入りのファイルを書いていた。そのため版 1 を読むときだけ、`title` の改行を許す。ほかの決まり（長さ・空白だけは不可）はそのまま確かめる
- 移した `content` にも、§3.3 の正規化と版 2 の決まり（V5）をかける
